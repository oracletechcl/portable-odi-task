A governed path from source control to a managed Spark execution.

The solution separates the customer-facing data logic from platform-specific deployment definitions. That gives delivery teams one tested codebase, repeatable promotion, and a clear option to move workloads as operating needs change.

How the pieces interact

From a small business rule to a repeatable cloud run.

The architecture deliberately gives each service one job. Source control holds the truth; CI/CD packages and verifies it; Object Storage carries immutable inputs, code, and releases; Data Integration coordinates; Data Flow executes Spark.

1

GitHub repository

Simulates the requested Bitbucket repository. It stores source, tests, environment descriptors, and deployment mappings.

2

CI/CD validation

GitHub Actions and a Bitbucket-compatible pipeline definition compile, test, package, and prepare deployment artifacts.

3

Object Storage

The private PoC bucket holds input data, Python, JAR, SQL, output, and exported release artifacts.

4

Data Integration

A pipeline sequence coordinates transform then validation, and can export the design as a release package.

5

Data Flow

Managed Spark applications execute the language-specific workload and write the verified result.

Business logic

Portable by design. Active-customer filtering, name normalization, tax calculation, and output validation live in testable code and SQL—not exclusively in visual orchestration operators.

Deployment logic

Platform-specific by choice. OCI scripts and external platform mappings describe how to submit the same logical workload to each supported runtime.

Governance

Controlled promotion. Environment YAML carries configuration. CI/CD validates an immutable artifact before it is promoted to TEST and then PROD.

What the data pipeline does

A concise, observable customer-data flow.

1. Transform customers

Read customer input, retain active records, normalize customer names, and calculate tax using a configurable tax rate. The result is written to the configured output location.

2. Validate the output

Check the produced dataset against the minimum-record count and quality expectations. A deliberately high threshold creates a controlled failure path that proves error handling is visible.

Language and platform portability

Choice without re-writing the core solution.

Language flavors

  • Python / PySpark — customer transform and validation workload
  • Java — Spark language probe packaged as a JAR
  • SQL — Spark SQL transform script
  • Scala — Spark language probe packaged as a JAR

Why this matters

Teams can keep their preferred Spark language while maintaining a common repository structure, validation discipline, data contract, and release process. This is a portability foundation, not an assertion that every runtime behaves identically.

Quality and delivery evidence

Validation is part of the release, not an afterthought.

Local and build checks

  • Python sources compile successfully
  • Automated test suite passes, including language-artifact coverage
  • Maven packages Java and Scala Spark probe JARs
  • OCI shell scripts pass shell syntax validation
  • Platform JSON and YAML mappings pass syntax checks

CI/CD behavior

The GitHub workflow is the active simulation of Bitbucket CI/CD, and a Bitbucket-compatible pipeline file is included for portability. Both validate the same source and package the same Java/Scala artifacts before OCI upload. This keeps the delivery contract independent of a particular Git-hosting provider.

Current limitation — authorization at the orchestration boundary. The Data Integration design, task, application, publication, and export were created successfully. The end-to-end Data Integration task run stopped before transformation because its workspace principal received NotAuthorizedOrNotFound when calling the Data Flow CreateRun API. IAM policies were assumed to exist, and this PoC did not create or modify any IAM policy. Direct Data Flow executions are therefore the confirmed execution evidence; pipeline-level success and failure propagation remain pending authorization remediation.

Recommended next steps

Turn the proven pattern into an operational delivery path.

  1. Have the tenancy administrator verify the documented least-privilege access of the Data Integration workspace principal to the Data Flow applications and runs in the PoC compartment.
  2. Map the Data Integration parameters for input path, output path, tax rate, and minimum-record count; then rerun the successful and controlled-failure pipeline paths.
  3. Promote the exported immutable release through TEST and PROD using environment-specific configuration only.
  1. Choose the next external runtime to operationalize and apply its repository mapping in that platform's own tenant/account.
  2. Run a small compatibility test on the target Spark version, storage connector, identity model, and logging destination.
  3. Set acceptance criteria for throughput, cost, recovery, and operational ownership before production rollout.
